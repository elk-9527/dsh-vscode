# 注释与文档规范

本文件定义本仓库中文文本的写作标准，适用于源码注释与 JSDoc、各 README、`docs/` 下的说明文档、
测试与工具脚本中的说明性注释，以及界面（webview）中面向用户的文案。

## 1. 目标

文本应当准确、客观、可核查。读者仅凭文本即可判断系统行为、约束条件与历史原因，
不需要借助语气、修辞或上下文推测。

## 2. 语言与语气

1. 使用陈述句。禁止反问句、设问句与感叹句。
2. 禁止比喻、拟人、夸张与俚语。
3. 不使用第一人称与第二人称，不出现「你」「我」「我们」。
4. 不使用口语化助词与语气词（「别」「不用」「就得」「其实」「反正」「嘛」「吧」「呢」等）。
5. 不使用主观评价词（「非常」「极其」「离谱」「要命」「一塌糊涂」等）。
6. 标题与列表项使用名词短语或动宾短语，不使用口号式表达。

## 3. 常见改写对照

| 原表述类型 | 改写方向 |
| --- | --- |
| 「开一扇门」「门太旧」「门不认识」 | 「提供接入点」「版本过低」「插件不支持该方法」 |
| 「掐掉」「撞车」「撑爆」「吃掉」「喂给」 | 「移除」「冲突」「超出上限」「丢弃并记录」「传给」 |
| 「顺手」「一眼就能看出」「白试」「瞎猜」 | 「同时」「可直接观察」「无效果」「推测」 |
| 「说白了」「其实是」「反正」 | 删除，直接陈述结论 |
| 「必须」「绝对不能」用于非强制约束时 | 改为「应当」「需要」，并说明依据 |

上表给出方向，实际以第 2 节的六条规则为准。

## 4. 必须保留的内容

1. 全部技术事实：数值、版本号、文件路径、函数名、协议字段、实验日期与结论。
2. 原因说明：为何采用当前实现，以及被否决的替代方案及其问题。
3. 已知限制、失败模式与错误码。

改写不得减少信息量。为符合语气要求而删除上述任何一类内容属于不符合本规范。

## 5. 术语

1. `dsh-acp-door` 在正文中统一称「ACP 接入点插件（`dsh-acp-door`）」，首次出现后可用「该插件」指代，
   不再单独使用简称。
2. 包名、代码标识符（`door`、`DoorClient`、`doorPermission` 等）、协议方法名、配置项名保持原样。
3. 既有技术术语（内核、会话、投影、预设、沙箱、批准策略等）沿用；首次出现时可附英文原文。
4. 「档」是 `profile` 在本仓库内部的既有简称，**允许在注释与说明文档中使用**，但不属于对外术语：
   面向用户的界面文案中不得出现（见第 6 节）。若某处单独出现会让读者无法判断所指，
   可在同段首次出现时写成「配置集（profile）」，其后仍可用「档」。
5. profile 的具体取值是配置数据的一部分，任何情况下保持原样：`desktop`、`vscode-panel`、
   `dshdoor`、`acp`、`$DSH_HOME/profiles`。
6. 日常用语中恰好含「门」字的词（专门、部门、自报家门等）不属于术语违规，无需改写。
7. 「兜底」属于口语化表述，按语境改为「后备」（名词，如「后备清单」「后备值」）或「回退」（动作）。
8. 「裸」在描述未经包装或未转义的数据时应改写：「裸换行」→「未转义的换行」、「裸命令」→
   「直接给出的命令」、「裸消息」→「未包装的消息」。
9. 「不认识」用于描述无法识别字段或方法时改为「无法识别」。该词出现在被引用的原始报文中时保持原样。
10. 「旁路」是既有技术术语，指该插件在内核之外自行应答请求，沿用不改。
11. 错误报文是跨包契约：插件 `packages/dsh-door/lib/index.js` 与扩展
    `packages/vscode-extension/src/dsh/permission.js` 的判定正则必须同步修改，
    且扩展必须同时保留对旧版插件文本的识别分支（用户机器上可能仍装着旧版插件）。

## 6. 界面文案

1. 适用第 2 节全部语言规则，但须保持简短。
2. 不得出现内部术语：包名、组件名、版本号、`profile`、设置项名。该约束由 `test/static.js`
   与 `tools/uitest.js` 中的黑名单断言保证，改写后这些断言必须继续通过。
3. 受控件宽度限制的文案（例如顶栏权限按钮）不得变长。
4. 文案变更必须同步更新钉住它的断言：`tools/uitest.js`、`test/panel.js`、`test/static.js`、
   `test/permission.js`。
5. `package.json` 中 `dshPanel.*` 配置项的 `description` 会显示在 VS Code 设置界面，按界面文案处理：
   适用本节全部约束，且不得出现「档」、包名与版本号。示例路径中的用户名使用占位符，
   不写入本机用户名。
6. 与桌面端逐字对齐的标签属于专名，不得改写：`仅可查看`、`工作区内修改`、`完全权限`、
   `Auto Approval`、`启用完全权限`。

## 7. 代码与行为约束

1. 只修改注释与文案。不得修改代码逻辑、标识符、协议字段、正则与断言中的技术取值。
2. 不得调整代码格式与换行，除非注释块本身需要重排。
3. `test/static.js` 以文本方式扫描其他源文件。不得在注释中引入可能被这些正则命中的字符串，
   例如在 `packages/vscode-extension/src/dsh/permission.js` 中写入 `'auto-approval':`。
4. 改写日志与诊断文本前，必须先检索该文本的匹配方。多处断言以子串匹配日志或协议报文，
   例如 `test/fallback.js` 匹配日志中的 `尝试启动` 与 `配置集：`，`test/presets.js` 匹配插件
   诊断日志中的 `记录=minimal`。改写这类文本而未同步匹配方，会使断言从「通过」变为「失败」，
   而失败信息只显示期望值与实际值，不显示原因。检索命令示例：
   `grep -rn "尝试启动" packages/`。
5. 改动协议报文（插件向客户端发送的错误文本）时，须同时确认两件事：客户端的分支判断仍能
   识别新文本（旧版客户端可能只识别旧文本，因此新文本应作为新增分支，而非替换），
   以及跨包一致性检查（`build/forward-compat-check.cjs`）通过。

## 8. 改写方法

按段落最小改写，保留原有段落结构与信息顺序。不进行全文重写，不合并或拆分既有注释块，
不改动注释所解释的代码。每段改完后自检：信息量是否减少、是否引入比喻、是否出现人称与语气词。

## 9. 验证

每批修改完成后运行以下检查，全部通过方可提交：

```sh
# ACP 接入点插件（纯函数套件）
cd packages/dsh-door
node test/frames.js && node test/permission.js && node test/port.js && node test/sessions.js

# VS Code 扩展（快速套件，含 static 契约与面板层）
cd packages/vscode-extension
node test/run-all.js

# 界面回放（无头 Chrome）
node tools/uitest.js
```

改动用户文案、权限协议相关文件或 README 中的命令示例时，追加：

```sh
node test/permission-live.js   # 需要本机已安装 DSH
```

文本层面的检查脚本位于 `tools/text/`（已纳入版本控制）。汇总入口一次运行全部检查，
任一项未通过时以非零码结束：

```sh
node tools/text/run-checks.cjs              # 基线默认为 HEAD（提交前比较工作区）
node tools/text/run-checks.cjs --base=<提交> # 提交之后用基线提交复现同一批证据
```

改动一经提交，工作区状态即为空，此时必须给出 `--base=<基线提交>`；在干净工作区上省略基线
运行覆盖面审计没有意义（改动集合为空，全部文件都会被列为「未被触及」）。

| 检查 | 命令 | 判定标准 |
| --- | --- | --- |
| 命中扫描 | `node tools/text/text-check.cjs` | 列出注释中的待改写表述；加 `--strings` 时改为只扫描字符串字面量行 |
| 代码改动核对 | `node tools/text/code-diff-check.cjs` | 与基线比较代码骨架，越界改动必须为 0 |
| 注释量核对 | `node tools/text/comment-volume.cjs` | 改写前后中文注释总量不得显著下降（阈值 25%） |
| 覆盖面审计 | `node tools/text/coverage-audit.cjs` | 列出「含中文但未被本次改动触及」的已跟踪文件；判定标准为「未被触及 0 个、无法读取 0 个」 |
| 跨包报文核对 | `node tools/text/forward-compat-check.cjs` | 同一批新旧报文输入分类函数，结果必须一致，且对外文案不含内部词 |
| 行尾与编码 | `node packages/vscode-extension/tools/check-eol.cjs` | 单个文件内不得混用 CRLF/LF，任何文件都不得带 UTF-8 BOM |

`code-diff-check.cjs` 的口径为：剥掉注释后不含中文的行视为代码骨架，逐文件与基线版本比较多重集合；
含中文的行必然只在注释、字符串、模板或正则里，因此单独统计。该口径有两处已知覆盖缺口：
含中文的正则字面量（例如 `/不认识权限方法/`）不参与比较，这类正则的改动由测试断言覆盖；
比较范围只含 `.js`、`.cjs`、`.mjs`，`.json`、`.yml`、`.css`、`.html` 的改动（例如 `package.json`
的市场描述与设置项文案）由 `test/static.js` 与人工核对覆盖。

各脚本一律以 `-z` 形式从 git 读取路径。默认输出会把非 ASCII 路径转义为八进制形式，这类路径
无法用于读取文件，会使含中文文件名的文件被静默跳过（覆盖面审计修正前漏算 8 份中文名文档）。

命中扫描器只做提示，不替代人工判断：命中项需逐条区分「确实违规」与「引文、夹具、正则、路径字面值」。
扫描规则本身也会误报与漏报，本文件中记录的词表随每次发现更新（例：排除 `分别` 中的「别」，
补入 `露出`、`关掉`、`藏着`、`拿掉` 等口语动词）。

## 10. 不在改写范围内的文本

以下文本是实验数据或执行输入，改写会使结论或产物失效，因此保持原样：

1. 发给模型的提示原文，例如测试与探针脚本中 `session.send('…')`、
   `data.content[].text`、请求参数里的 `prompt` 字段。
2. 会话与历史记录的夹具数据，以及用于生成截图的构造数据（`spike/history-shots.cjs`、
   `spike/measure-history.cjs` 等）。
3. `spike/capture/` 下的实验抓包与 `spike/scratch/` 下的临时产物
   （其中 `spike/scratch/hello.ts` 由 `test/smoke.js` 使用，不得删除）。
4. 协议取值、界面标签与错误码等字面值。
5. 已被测试或工具正则匹配的字符串：这类字符串属于对外契约，只有在同步修改匹配方时才能改动。
   判定方法为在仓库内检索该字符串，确认引用位置。
6. 由脚本生成、供界面断言比对的冻结快照（`packages/vscode-extension/build/uitest/`）：其内容与
   `tools/uitest.js` 内的期望值配套，改写需与快照重新生成成对进行，收益与风险不成比例。

## 11. 引文与历史记录

1. 引用用户原话、旧版界面文案、旧版报文的句子，引号内文字逐字保留：它们是结论的依据，
   改写会使记录失去可核查性。引号外的叙述按第 2 节规则改写。
2. 测试中用于验证兼容性的旧文本夹具（例如 `packages/vscode-extension/test/permission.js` 中
   的旧版插件报文）逐字保留，它们本身即是被断言的对象。
3. 引用旧文案时，若该文案已被改写，注释应同时给出当前文案，避免读者误判现网行为
   （例：`packages/vscode-extension/media/main.css` 在说明 `[hidden]` 失效现象时引用的是
   当前按钮文案）。
4. 历史记录类文档（`docs/交接文档.md`、`docs/本轮改动与后续步骤.md` 等）按时间顺序记录当时的
   状态与当时的文案。记录「当时的面板显示什么」时保留当时文本；描述「现在是什么」时使用当前文本。
