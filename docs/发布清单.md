> 日期：2026-09-20　状态：**发布准备已完成，填完占位符并执行发布命令即可发布**。
> 发布所需凭据（VS Code 的 PAT、npm 的 token）**不存放在本仓库中，也不应进入本仓库**，
> 需要先在两个平台注册账号，再将凭据填入环境变量。

本项目发布到**两个相互独立**的市场，每个市场各有一个包：

| 包 | 发布目标 | 审核方式 | 发布命令 |
| --- | --- | --- | --- |

## 0. 当前阻塞项：三个占位符

三处填写的是 `TODO-...`，执行发布脚本时会被明确拒绝（原因不是遗漏，而是**禁止携带占位符发布**：
携带占位符发布，轻则返回 403，重则发布到并非该账号所属的 publisher 名下，或导致市场页面上的链接
全部指向其他仓库）。

| 占位符 | 出现位置 | 替换值 |
| --- | --- | --- |
| `TODO-your-publisher-id` | `packages/vscode-extension/package.json` | 该账号在 VS Code 市场的 publisher ID（= Azure DevOps 组织名） |
| `TODO-owner` / `TODO-repo` | 根 `package.json`、两个包的 `package.json`、`README.md` | GitHub 账号与仓库名 |

一次性完成替换（PowerShell；**使用 .NET 写入文件，不使用 `Set-Content -Encoding UTF8`** ——
后者会添加 UTF-8 BOM，ACP 接入点插件（`dsh-acp-door`）的 package.json 曾因此损坏用户的档，事故记录见
`packages/vscode-extension/test/static.js` 中的 BOM 断言）：

```powershell
cd D:\dsh-vscode
$owner = '<GitHub 账号>'
$repo  = '<仓库名>'
$pub   = '<VSCODE-PUBLISHER-ID>'

$files = git ls-files | Where-Object { $_ -match '\.(json|md|yml|yaml|js|cjs|mjs)$' }
foreach ($f in $files) {
  $p = Join-Path (Get-Location) $f
  $t = [IO.File]::ReadAllText($p)
  if ($t -notmatch 'TODO-owner|TODO-repo|TODO-your-publisher-id') { continue }
  $t = $t -replace 'TODO-owner', $owner -replace 'TODO-repo', $repo -replace 'TODO-your-publisher-id', $pub
  [IO.File]::WriteAllText($p, $t, (New-Object Text.UTF8Encoding($false)))
  "  改写 $f"
}
```

修改完成后执行自检（两项输出应全部为 ✅）：

```powershell
node packages/vscode-extension/tools/publish.js     # 彩排：将执行到 vsce package 这一步
node packages/dsh-door/tools/publish.cjs            # 彩排：npm pack --dry-run + 输出待提交的 PR 内容
```

**仓库需先推送至远端。** 本仓库目前没有 remote，两个市场均要求先提供公开仓库：

```powershell
git remote add origin https://github.com/<owner>/<repo>.git
git push -u origin main
```

同时在 GitHub 仓库页面上完成两项设置：
1. 添加 **`dsh-plugin`** topic（DSH 精选列表的硬性要求，Settings → Topics）。
2. 确认仓库为 **public**，且创建时间已 **满 1 天**（CI 会自动检查该项：创建时间过短的仓库会被判定为
   "PR 前几分钟才建好的占位仓库"并拒绝；该判定不针对项目本身，满足条件后重新提交即可）。

`https://marketplace.visualstudio.com/items?itemName=<publisher>.dsh-panel`

### 发布包内容核对

23 个文件，335 KB：`package.json`、`README.md`、`LICENSE`、`CHANGELOG.md`、
`src/**`（11 个 js）、`media/**`（`main.js`/`main.css`/`markdown.js`/`dsh.svg`/

**测试、诊断工具、界面截图工作目录与 docs 均不进入发布包**，由两份**互为后备**的清单控制：

### 版本号规则

市场**不接受重复发布同一版本号**（即使"仅修改 README"也计为一次更新，同样需要更换版本号）。发布前应先确定发布方式：

| 写法 | 适用场景 |
| --- | --- |
| `node tools/publish.js --yes --patch` | 修复 bug / 修改文案这类小改动（0.1.3 → 0.1.4） |
| `node tools/publish.js --yes --minor` | 新增功能（0.1.4 → 0.2.0） |
| `node tools/publish.js --yes --major` | 不兼容的重大改动（0.2.0 → 1.0.0） |
| 先手动修改 `package.json` 的 `version` 并提交，再执行 `node tools/publish.js --yes` | 需要自行控制版本号，或需要手工编写该提交 |

带版本参数的三种方式均调用 `npm version`，该命令**会自动生成一笔版本提交 + 一个 tag**，
因此**工作区必须先干净**（脚本会代为检查，工作区不干净时直接拒绝，不会在发布中途失败）。

细节与"后续每次更新需执行的 7 个步骤"见下文 **第 3 节**。

### 撤回方式

```powershell
npx --yes @vscode/vsce unpublish <publisher>.dsh-panel        # 仅下架
npx --yes @vscode/vsce unpublish <publisher>.dsh-panel --force # 连同数据一并删除（不可逆）
```

## 2. DSH 插件市场（`dsh-acp-door`）

### 插件定位

DSH 的"插件市场"**不是一个上传后台**，其构成为：① 客户端中的市场插件
（`dsh-market` / `dsh-community-market`）与 ② 目录站 —— 两者读取同一份**精选列表**：
[`awesome-dsh-plugin/awesome-dsh-plugin`](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin)。

因此"上架"= **发布 npm 包（可选但推荐）+ 向该列表提交一个 PR**。该 PR 仅新增**一个文件**。

### 一次性准备

1. npm 账号（<https://www.npmjs.com/signup>），随后执行 `npm login`。
   已确认 `dsh-acp-door` 这一包名**在 npm 上尚未被占用**（2026-09-20 查询：registry 返回 404）。
2. 使 `package.json` 的 `repository` 指向本仓库 —— npm 侧的映射为**自动采集**，
   依据即该字段；未指回本仓库时不会关联到列表条目。

### 发布

```powershell
cd packages/dsh-door
node tools/publish.cjs             # 彩排：自检 + npm pack --dry-run + 输出待提交的 PR 内容
node tools/publish.cjs --yes       # 正式发布到 npm
```

包内只有 10 个文件、35 KB：`package.json`、`README.md`、`CHANGELOG.md`、`LICENSE`、
`cordis.patch.yml`、`lib/*.js` 五个。测试、`tools/`、`assets/`（截图）、`*.tgz` 均不进入发布包
（由 `files` 字段控制）。

### 提交 PR（单个文件即全部投稿）

脚本会输出待提交内容，直接写入 `data/plugins/<owner>__<repo>--packages-dsh-door.yml`：

```yaml
url: https://github.com/<owner>/<repo>/tree/main/packages/dsh-door
name: <owner>/<repo>#dsh-door
category: dev
description:
  en: 'Loopback-only ACP door for DeepSeek Harness: attach an external client (such as the DSH Panel VS Code extension) to the kernel you already have running, exposing session listing and permission presets.'
  zh: 为正在运行的 DeepSeek Harness 内核新增一个仅监听本机回环地址的 ACP 接入点，供外部客户端（如 VS Code 的 DSH 面板）连接同一个内核，并接出会话列表与权限预设。
```

规则（来自上游 `contributing.md`，2026-09-20 逐条核对）：

- 文件名 = `<owner>__<repo>.yml`；monorepo 子包在仓库名后接 `--` 与子目录名
  （`packages/dsh-door` → `--packages-dsh-door`）✓ 脚本按该规则生成。
- 条目中 `name` 的 `#dsh-door` 为**子目录名**（按上游规则填写："subname 就是子包路径"）。
  需注意子目录名为 `dsh-door`、而包名为 `dsh-acp-door` —— **用户安装时使用包名**
  （`dsh plugin add dsh-acp-door`），两者不一致属于正常情况，并非填写错误。
- `description.en` 中**含 ": " 时必须加引号** —— 条目中的英文描述恰好包含（"Harness: attach …"），
  脚本已写成单引号，复制时不应去掉引号。`zh` 为可选字段（不填写时由维护者补充）。
- `category` 只能取以下值：
  `agi` `ui` `usage` `theme` `model` `identity` `session` `memory` `tools` `wsl` `browser`
  `vision` `voice` `docs` `skill` `workflow` `git` `notify` `dev` `security` `remote` `market` `fun`。
  本项目选择 **`dev`**（其本质为开发与集成使用的传输层）。分类选择不准确不会影响提交 —— 说明中写明
  "没人会因为分类被打回，维护者直接改"。
- **不应手工编辑上游的两个 README**，它们由脚本从 `data/plugins/*.yml` 生成。
- 单个 PR **最多 3 条**。
- 描述**必须属实**（维护者会对照代码阅读）：条目中填写的是"只监听本机、会话列表与权限预设"，
  与实现一致 ✓。这也意味着**不应添加营销词**。
- 硬性要求：仓库已声明 `dsh.bundle`（本仓库为 `dsh.bundle.patch` ✓，位于
  `packages/dsh-door/package.json`，同目录下的 `cordis.patch.yml` 亦已提供 ✓）、包含真实代码、
  仓库创建满 1 天、具有 `dsh-plugin` topic。
- 官方 `@deepseek-ai/*` 包必须使用 `peerDependencies` 而非 `dependencies`：
  本包仅依赖 `@agentclientprotocol/sdk`（第三方），不涉及该条 ✓。
- npm 映射**无需在 yml 中写入任何字段**：手工写入 `npm:` 键会被校验**拒绝**。

### 截图（可选，推荐）

市场详情页可像 App Store 那样展示截图。上游当前要求**将清单存放在本仓库内**：
`packages/dsh-door/screenshots.json`（与 `package.json` 同目录），列出 1–8 张、路径相对于该文件：

```json
["assets/panel-chat.png", "assets/panel-permission.png"]
```

### 不发布 npm 的备选方案

如不发布 npm，可将打好的 tgz 上传到 GitHub Release，然后在条目中增加一行
`tarball: https://github.com/<owner>/<repo>/releases/latest/download/dsh-acp-door.tgz`。
**注意**：`latest/download/` 仅在请求时解析 `latest`，文件名按字面取值 ——
文件名中包含版本号时，发布下一版后会返回 404。文件名应当不带版本号，或固定 tag
（`.../releases/download/v0.0.12/dsh-acp-door-0.0.12.tgz`）。

### 撤回方式

- npm 上的发布在 **72 小时内**可执行 `npm unpublish dsh-acp-door@<版本> --force`，超过该时限只能
  执行 `npm deprecate`（改为发布新版本修复问题）。
- 列表条目：向 `awesome-dsh-plugin` 提交一个删除本仓库对应 yml 的 PR。

## 3. 后续更新流程

### 仅更新 VS Code 扩展：7 个步骤

```powershell
cd D:\dsh-vscode\packages\vscode-extension

# 1) 修改代码（src/ 与 media/；这两个目录即打包进包的全部前端与逻辑）
# 2) 运行测试，全部通过后再进行后续操作
node test/run-all.js --all          # 19 个套件
node tools/uitest.js                # 界面回放 494 项（仅在修改界面时需要，单次运行约数十秒）
node tools/check-eol.cjs            # 检查是否存在混用的 CRLF/LF 与 BOM

# 3) 编写 CHANGELOG.md（市场页面的「Changelog」标签读取该文件）+ 确定版本号
#    最新一节置于文件最上方，格式按现有条目复用：
#    ## [0.1.4] — 2026-09-21
#    ### 修复 / ### 变更

# 4) 先在本地安装一次，确认可实际使用（市场更新不会自动更新手动安装的那一份，见下文）
node tools/build-vsix.js
code --install-extension build\dsh-panel-0.1.4.vsix   # 版本号按实际情况调整
node tools/check-installed.cjs                        # 输出应当"逐字节一致"
#   → 随后打开 VS Code 验证（Reload Window）

# 5) 彩排：自检 + 打市场包 + 列出文件 + 两条打包路径比对（不发布任何内容）
node tools/publish.js

# 6) 正式发布（先设置 token；更换版本号时追加 --patch/--minor/--major/--version）
$env:VSCE_PAT = '<token>'
node tools/publish.js --yes --patch

# 7) 提交 + 推送 + 刷新备份
cd D:\dsh-vscode
git add -A; git commit -m "0.1.4：……"; git push
#   备份按 docs\恢复方法.md 末尾的命令执行（bundle + 源码快照 + vsix + 档记录 + 还原演练）
```

### 三个常见问题

1. **本地安装的版本不会自动同步。** 由 `.vsix` 安装的扩展，VS Code 记录的来源为
   `source: vsix`，与"从市场安装"不同 —— 市场发布新版本后，本地安装的那一份**不一定**
   随之升级（很可能长期停留在旧版本）。因此第 4 步每次均需执行，否则会出现对照市场的新版本页面、
   测试本地旧版本，并据此误判"我改的东西没生效"的情况。
2. **市场页面存在若干缓存点**：版本号与 CHANGELOG 在数分钟内更新；README 中的图片
   若同名同址，浏览器与市场可能仍使用旧文件，更换文件名最为简便。
3. **发布错误只能通过发布新版本修复**：`unpublish` 仅执行下架（已安装用户的版本不会回滚），
   已安装的用户只会向**更高**版本升级。因此确需撤回时，正确做法是发布一个更高版本修复问题。

### 另一条发布线：DSH 侧插件（`dsh-acp-door`）

该插件的**版本号与扩展相互独立**，发布渠道亦独立：

```powershell
cd D:\dsh-vscode\packages\dsh-door
# 1) 修改 lib/ → 运行测试（测试套件包含在扩展侧的 run-all.js 中）
cd ..\vscode-extension; node test\run-all.js --all
# 2) 编写 packages\dsh-door\CHANGELOG.md，并将 package.json 的 version 递增（例如 0.0.13）
# 3) 彩排（npm pack --dry-run + 检查 dsh.bundle / screenshots.json 等 + 输出列表条目）
cd ..\dsh-door; node tools\publish.cjs
# 4) 正式发布（先执行 npm login）
node tools\publish.cjs --yes
```

发布到 npm 之后，**列表条目无需重新提交**（npm 的映射为自动采集）；仅在更换仓库地址、
分类或描述时，才需要向 `awesome-dsh-plugin` 提交新的 PR。用户端的更新命令为
`dsh plugin --profile <档名> add dsh-acp-door`（安装完成后重启内核/桌面端）。

## 5. 隐私 / 安全（发布前需再次核对）

- **`docs/*.md` 中包含本机的绝对路径**（`D:\dsh-vscode`、`C:\Users\Lenovo\...`、
  备份目录名）。这些文件**不进入任何发布包**（两个包的白名单中均无 `docs/`），
  但它们会随仓库一同公开 —— 这些内容属于工作记录，公开发布前可自行决定是否保留。
  同类情况还有 `spike/`（早期探针脚本）与 `packages/*/tools/`。
- ACP 接入点插件（`dsh-acp-door`）**仅监听 `127.0.0.1`、不含鉴权**。这是有意设计（本机自用），其含义是
  **同一台机器上的任何程序**均可连接并驱动本机的 DSH。该限制已在两个 README 中写明，不应改为 `0.0.0.0`。
- 仓库中**不含**任何 token / cookie / 会话内容：`*.tgz`、`backup/`、`shots/`、
