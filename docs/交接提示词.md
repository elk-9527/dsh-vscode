### 2. 项目是什么

在 VS Code 侧边栏中使用用户自己的 DSH —— 不是第二个 agent。接入桌面端时使用同一个
运行内核；自行启动时使用同一份 `$DSH_HOME` 下已准备的配置集。

```
VS Code 侧边栏（扩展 dsh-panel：webview + ACP 客户端）
      │  ACP：JSON-RPC，一行一个 JSON（NDJSON）
      ▼
ACP 接入点插件 dsh-acp-door（安装在 DSH 内核中，在回环地址再提供一份 ACP；默认 127.0.0.1:47821）
      │
      ▼
正在运行的 DSH 内核（用户的桌面端，或扩展自行启动的无窗口内核）
```

接入正在运行的桌面端时，面板使用**同一个运行内核**。自行启动时，面板使用同一份
`$DSH_HOME` 下的 `vscode-panel` 配置集：会话与记忆目录仍由本机 DSH 管理，但配置集内的
插件、模型与设置不会自动从 `desktop` 复制，必须在该配置集中分别准备。

两个包都必须安装，缺一不可：

| 包 | 目录 | 形态 | 发布目标 |
| --- | --- | --- | --- |
| `dsh-panel` | `packages/vscode-extension/` | VS Code 扩展，本身即 ACP 客户端 | VS Code 市场（`.vsix`） |
| `dsh-acp-door` | `packages/dsh-door/` | DSH 插件（ESM），提供接入点 | npm + DSH 插件精选列表 |

两条运行路径都是主路径，不是后备：

- 端口上已有接入点（桌面端在运行）→ 面板直接接入：一个进程、一个内核。
- 端口上没有接入点（桌面端未启动）→ 面板自行启动一个无窗口内核，
  关闭 VS Code 时回收自行启动的进程，不触碰桌面端的进程。

接入点插件只监听 `127.0.0.1` 且**没有鉴权**，因此本机任何进程都能连接该端口。
这是有意设计，也是已向用户披露的安全边界，不得改为 `0.0.0.0`，不得引入需要用户填写凭据的鉴权。

**零运行时依赖是刻意选择**：手写 NDJSON 客户端、纯 CommonJS 扩展、ESM 插件、不使用打包器与框架。
后续修改应当保持这一风格；引入依赖前需要先向用户说明理由。

```powershell

```

三条需要留意的判据：

1. **项数每次运行可能不同，判据是"是否全部通过"，不是项数。** 文档中记录的项数属于当时的快照。
2. **真实回合需要模型额度。** 内核返回 429（`GoUsageLimitError`）时，`smoke.js` / `resume.js` /
   `presets.js` / `fallback.js` / `panel.js` 中的真实回合会失败 —— 这属于额度问题，不表示代码损坏。
   报告时必须写明这一区别，不得直接说"测试失败"。
3. **`dsh` 不在 PATH 上时，真实内核套件需要先设置
   `$env:DSH_PANEL_DSH = "<node.exe 完整路径> <bin.js 完整路径>"`**，否则这些套件失败，
   同样并非代码损坏。

另有一条已知的副作用：运行测试会向用户共享的会话库 `$DSH_HOME/sessions` 写入会话记录（`dshdoor` 档的测试产物）。
这属于既有行为，不得代为清理用户本人的会话记录。

2. **不得删除用户的文件**，包括 `$DSH_HOME/sessions` 中的会话记录与用户已有的备份。
3. **不得破坏现有编译与测试环境。** 测试只使用 `dshdoor` 档；需要真实内核的测试自带端口选择，
   不得假定某个端口为空。
4. **每完成一步提交 git**（中文提交信息，使用 `git commit -F <文件>`）。当前没有 remote，
   不得自行添加 remote 或推送；地址与授权由用户提供。
5. **不得索取、读取或打印任何 token、PAT、密钥、恢复码。** 发布凭据由用户自行写入环境变量。
6. **不明确的地方先询问用户，不得自行推断。** 一次问完，用通俗的中文表述，必要时给出选项与推荐项。
7. **结论必须有证据**：日志原文、命令输出、测试结果。未实际执行或未实际验证的事，

面向用户的文本与面向维护者的文本适用两套标准，不得混用。

- **表达方式**：使用陈述句，不使用比喻、拟人、夸张与口语化表达，不使用第一人称与第二人称。

  这两条规则由 `test/panel.js`（§8.7、§8.9）、`test/permission.js`、`test/static.js`、
  `tools/uitest.js` 中的断言守卫，用户已就同一问题提出过两次，不得回退。

### 6. 已知陷阱（最易踩的一批；完整 26 条见 `docs/交接文档.md` 第八节）

1. **PowerShell 5.1 不得用于写文件。** `Set-Content -Encoding UTF8` 会写入 UTF-8 BOM，
   该事故曾使插件的 `package.json` 带 BOM、安装进用户的档后 `dsh plugin` 每次都在 `JSON.parse` 失败，
   等同于损坏该档。修改文件一律使用编辑工具；读取 JSON 使用 Node，不使用 `ConvertFrom-Json`；
   不要用内联 `node -e "…"`（中文、引号与反引号会被吞），写成 `.cjs` 文件后执行。
2. **不得按进程名终止内核。** 用户桌面端启动的内核与扩展启动的内核外观相似；
   自检工具只回收自己开启的隔离窗口，其余仅作报告。
3. **等待接入点必须使用 `waitForPort`**，`probePort` 是单次探测，会产生假阴性。
4. **切换模型以内核回复为准**（`setSessionConfigOption` 返回的 `configOptions`），
   不得以请求值作为依据，内核会归一化取值。
5. **会话读取有两份实现**（插件 ESM 一份、扩展 CJS 一份，原因是扩展零依赖）。
   任一侧修改都必须同步另一侧，`test/sessions-parity.js` 负责约束一致性。
6. **改动文案或日志文本之前先检索匹配方**：多处断言以子串匹配日志与协议报文，
   不同步修改会使断言从通过变为失败，而失败信息只显示期望值与实际值，不显示原因。
   例：`grep -rn "尝试启动" packages/`。
7. **测试不得假定某个端口为空**：用户可能正在运行面板（47831）或桌面端（47821）。
   历史上曾因该假定导致两条路径根本没有被执行。
8. **`build/` 会被打包脚本清空**：`node tools/build-vsix.js` 执行 `rmSync(build)`，
   需要保留的产物不得放在该目录（截图因此丢失过一次）。
9. **打包文件清单只有一份权威来源**：`packages/vscode-extension/tools/ship-list.js`（白名单）
   与 `.vscodeignore`（黑名单）必须一致，`tools/publish.js` 每次彩排都逐文件比对两条打包路径。
   新增随包文件时漏改其中一处，会造成"本地安装正常、市场用户安装缺文件"。
10. **`local.dsh-panel` 这类扩展 ID 不得写死。** 安装目录名依据 `package.json` 的
    `publisher`+`name`+`version` 计算；更换 publisher 等同于更换扩展 ID，
    旧版本会残留在磁盘上并被扫描加载，必须卸载并手动删除残留目录，否则会出现两个面板。
11. **无头 Chrome 不为程序化滚动派发 scroll 事件**（实测 0 次）。`tools/uitest.js` 中采用手动派发，
    该处注释已写明原因，不得按"直接测试"简化。
12. **`tools/uitest.js` 中的断言脚本是模板字符串**：注释与代码中均不得出现反引号，
    换行必须写作 `\\n`，否则生成的脚本直接产生语法错误。

### 7.1 发布路径：两种做法，优先用仓库里的脚本

用户当前已能打开市场的管理页面（`marketplace.visualstudio.com/manage`），
页面上是「Upload Visual Studio Code extension / Drag and Drop a file here or click to upload」。
该路径**可行，但不是本仓库的首选**，原因是它只做上传，不做本仓库发布脚本里的三项检查。

| 做法 | 它做了什么 | 风险 |
| --- | --- | --- |
| `node tools/publish.js --yes`（扩展）、`node tools/publish.cjs --yes`（插件） | 自检（publisher 是否为占位符、`repository` 是否真实、图标与 CHANGELOG 是否在）→ 打包 → 逐文件比对两条打包路径 → 按版本参数递增版本号并生成版本提交与 tag → 发布 | 无；这是仓库准备好的路径 |

### 8. 每轮交付标准

一轮改动必须走完下列步骤，缺项即视为本轮未完成：

1. 修改代码（`packages/vscode-extension/src`、`media`，或 `packages/dsh-door/lib`）。
2. 运行 `node test/run-all.js`；涉及真实内核、界面或文案时追加 `--all`、`tools/uitest.js`。
3. 运行中文文本门禁：`node tools/text/run-checks.cjs --base=<改动前的提交>`（改动过中文文本时）。
4. 装进 VS Code 实测：`node tools/build-vsix.js` → 安装 → `node tools/check-installed.cjs`
   （输出应为逐字节一致）→ 提示用户执行一次 Reload Window。改动界面时先运行
   `node tools/preview.js` 与 `node tools/shots.js` 生成前后对比截图。
5. 更新 `packages/vscode-extension/CHANGELOG.md` 与版本号（市场不接受重复发布同一版本号；
   改文案也计为一次更新）。
6. 更新受影响的文档与钉住文案的断言（两者必须同批修改）。
7. `git commit`（中文提交信息，写清改了什么与为什么）。需要回退时按 `docs/恢复方法.md` 执行。
8. 刷新整仓备份（命令在 `docs/恢复方法.md` 末尾：bundle + 源码快照 + vsix + 档记录 + 还原演练）。

### 9. 汇报格式

每轮结束时按下述四项汇报，避免让用户从长段落中提取结论：

1. **结论**：改了什么、当前是否可用。
2. **证据**：实际运行的命令与关键输出（测试统计、自检项数、日志关键行）。
3. **未验证项**：没有实际验证的部分，写明原因（例如模型额度耗尽、桌面端正在运行）。
4. **下一步**：需要用户提供的信息或需要用户执行的操作（例如 Reload Window）。

### 10. 明确禁止过的事情（历史上发生过）

- 声称完成而实际未执行（插件升级事件），或把推测写成结论。
- 为了让失败消失而修改断言的期望值，而不是定位原因。
- 为节省一个进程而牺牲功能：优先接入现成的旧版内核曾导致权限功能整体不可用，
  而用户只会认为"你的东西坏了"。
- 在界面文案中写入内部术语（用户提出过两次）。
- 让界面文案变长（用户提出过两次）。
- 删除或清理用户的会话记录、备份、桌面档内容。发现问题时报告并等待用户确认。
