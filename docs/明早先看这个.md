## 二、修掉的真 bug（4 个，都有回归测试）

### 1. dsh 的路径里有空格就起不来（他"修了一半"）

**症状**：面板连不上、也不会自己拉起后台内核，报的错是
`'C:\Users\…\Roaming\DSH' is not recognized as an internal or external command`
（cmd 的原话；面板会把它翻成中文人话"不是内部或外部命令"再给你看）。

**根因**（两个独立缺陷叠在一起）：

- 你的 `dsh` 真路径是 `…\AppData\Roaming\DSH Desktop\host-commands\…\dsh.cmd`，
  **路径里有空格**。原来的代码把命令按空白硬拆，于是程序名被劈成两段。
  而设置项和面板的报错文案又都告诉用户"把完整路径填进设置"——用户照做就中招。
- 就算用户自己加了引号也没用：`spawn(cmd.exe, [...])` 会把参数里的引号**再转义一遍**，
  cmd 收到的是坏掉的路径。必须同时给 `windowsVerbatimArguments: true`。

**修法**：`resolveCommand()` 先看"整串是不是一个存在的文件"（是就整段当程序名），
否则按空白拆、再按"磁盘上真的存在的那一段"把拆坏的片段粘回去。
配了一个**真进程**回归套件 `test/spawn-quote.js`（16 项：造一个带空格的 `.cmd`
垫片，用真的拉起逻辑去跑它，再读垫片收到了什么）。

**为什么这件事最要紧**：这是**你这台机器上必然会踩**的 —— 你的 dsh 路径就带空格。

### 2. 一次失败的建会话，会把预设串到下一段对话

**症状**：你明明没点名、或点了另一个模式，新会话却挂上了上一次那个模式。
只在"有一次建会话失败"之后才出现，最难查的那种。

**根因**：门记住"客户端点名了哪个预设"是靠一个队列（`session/new` 时还不知道
会话 id，只能按发出顺序排队，等 `agent/created` 来领）。但请求**失败**时不会有
`agent/created` 来领，那一条就一直留在队首 —— 被**下一次**建会话领走。
出错的回复压根没被处理，因为预筛那行写着"这行里得有 `result`"。

**修法**：出错的回复也要处理 —— 把那次点名从队列里摘掉。回归测试盯着这条。

### 3. 消息有可能永远发不出去（且毫无提示）

**症状**：极端情况下你发了消息，界面上什么反应都没有，也没有任何报错可查。

**根因**：入站方向有一道闸，会话的预设挂完之前会把 `session/prompt` 按住
（这是对的，不按的话模型手里一个工具都没有）。但它**没有超时**：
`await waiting.catch(() => {})`。挂载链内部全都 catch 过了，唯一漏网的是内核
某个服务返回一个**永不落定**的 promise —— 那时这句话就被永久按住。

**修法**：入站和出站用同一个上限（15 秒），到点放行。最坏退化成"这个会话手里
没工具"（看得见、能重试），而不是"消息石沉大海"。

### 4. 读历史失败时，说的是"门太旧，重启桌面端试试"——重启多少次都没用

**症状**：点历史按钮，得到一句"门插件太旧（需要 dsh-acp-door 0.0.8 以上）。
重启桌面端 DSH（或重装门插件）后再试。" 照做之后，还是同一句。

**根因**：门是装在**用户档**里的插件，而那个档由 DSH 桌面端自己管理。
桌面档里装的门是 **0.0.7**，而且**升不上去**（桌面端跑着的时候 CLI 直接拒，
见下面第三节）。所以这句提示把"扩展自己的依赖问题"转嫁给了你，而且给的出路是死的。

**修法**（这也是今晚最有价值的一处）：**面板不再依赖门的版本**。
连的是本机时，历史会话由**面板自己读** `$DSH_HOME/sessions` —— 它和内核本来就在
同一台机器上，会话文件就在磁盘上，没有任何理由读不了。门的那两个旁路方法仍然
优先用（连**别的机器**上的门时只能靠它），门太旧就自动退回自己读，**不再打扰你**。

实测：**86 段会话、0 段解码失败、1.34 秒**读完。

### 外加两套一直红着的测试
