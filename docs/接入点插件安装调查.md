### Answer to the direct question

A manual edit to `profiles\desktop\package.json` **can** survive a DSH Desktop restart: nothing
in the app regenerates the `dependencies` block, and `ensureDesktopProfile()` preserves it. But
the file is **not protected**: real `pnpm` runs inside the profile directory on every market
install/update (`pnpm add/remove` rewrites `package.json` + `pnpm-lock.yaml`), the app rewrites
`dsh.profile.bundles` when it reorders, and the app keeps its own checkpoint copies that a UI
"restore checkpoint" can write back.

## 6. Recommendations for a maintainer (so a 0.0.8 upgrade STICKS)

**6.1 Install it, don't just edit it.** A manifest edit alone is invisible to the runtime: the
upgrade only takes effect when pnpm materializes `node_modules` + `pnpm-lock.yaml` for the new
specifier. Use the product's own path from a shell:

```
dsh plugin --profile desktop add "file:<仓库根目录>/packages/dsh-door/dsh-acp-door-0.0.8.tgz"
```

That is exactly what the plugin's own README prescribes (copy found in the pnpm store,
`…\README.md` line 151: `dsh plugin --profile <profile> add "file:<本目录>\dsh-acp-door-<版本>.tgz"`).
It runs real `pnpm` in the profile dir **and** runs `reconcilePlugins()` so the package joins
`dsh.profile.bundles`. *(Not executed here — this task was read-only and forbids
`dsh plugin --profile desktop add/remove`.)*

**6.2 If you must hand-edit `package.json`**, you must follow it with a pnpm run inside
`$DSH_HOME\profiles\desktop`. Then verify on disk, because that is what actually decides:
* `…\node_modules\dsh-acp-door\package.json` → `"version": "0.0.8"`
* `…\node_modules\dsh-acp-door\lib\sessions.js` exists (0.0.8-only file)
* `…\pnpm-lock.yaml` → `specifier: file:<仓库根目录>/packages/dsh-door/dsh-acp-door-0.0.8.tgz`
* `$env:LOCALAPPDATA\pnpm\store\v11\file+D++dsh-vscode+packages+dsh-door+dsh-acp-door-0.0.8.tgz` exists
* restart and check the 0.0.8-only method `dsh-door/sessions/list` answers instead of "Method not found"

**6.3 Expect later rewrites (this is what makes hand edits fragile).** Any market install/update
runs pnpm in the profile dir and rewrites `package.json` + `pnpm-lock.yaml` (today: the
`dsh-context → 0.53.3` update at 00:05:22 was the last writer). The app rewrites
`dsh.profile.bundles` at startup when the order changes. Keep `dsh-acp-door` in both
`dependencies` and `dsh.profile.bundles`.

**6.4 Watch the app's checkpoints.** The app keeps three healthy-startup copies of the profile
manifest at
`$env:APPDATA\DSH Desktop\health-snapshots\8fe591330ce1dca4c4b0fa960743939e017cb0ed50052938ae9c416a568a4d9d\slot-{1,2,3}\`
(`package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `cordis.patch.yml`, `.dsh-market\state.json`, `home\settings.yaml`).
`slot-1` (2026-09-17 13:36) and `slot-2` (2026-09-17 16:06) still hold `dsh-acp-door 0.0.7` +
`dsh-context 0.53.1`; `slot-3` (2026-09-19 00:05:52, captured by the healthy boot after the market
update) holds 0.0.7 + 0.53.3. A UI checkpoint restore
(`DesktopProfileCheckpoint.restoreSlot`, `profile-channel-admission-CVuyDpHt.js`) **will** write
those files back and schedule dependency re-materialization — that is the one genuine
"regeneration" vector, and it is user-triggered.

**6.5 A 0.0.8 upgrade can stick** — it will stick exactly as long as it is installed through
pnpm and nobody restores a pre-upgrade checkpoint. It can **not** stick if only the
`package.json` text is changed, or if the change is made while the app is running and then any
market operation runs pnpm before the edit is materialized.
