## 一、项目内容与目标

**要点**：在 VS Code 的侧边栏中使用用户自己的 DSH —— 不是另一个 agent。接入桌面端时
使用同一个运行内核；自行启动时使用同一份 `$DSH_HOME` 下的网页配置集。会话与记忆目录仍由
本机 DSH 管理，但配置集内的技能、插件、模型与设置不会自动从桌面端复制，必须分别准备。

**原始目标的五个子项**（取自任务书）：

1. 连接层：能够连接 DSH 的 ACP 接入点插件（`dsh-acp-door`）；端口上没有该插件时
   **由面板自行启动一个内核**（共用同一份 `$DSH_HOME`，因此共用同一份记忆与会话记录）——
   **不要求用户先打开桌面端**（用户 2026-09-19 明确强调过这一条）。
2. 侧边栏面板支持完整对话：流式输出、工具调用展示、中断、模型与预设切换、上下文用量。
3. 建立自测试与迭代循环，反复定位缺陷 → 修复 → 重测，直到稳定。
4. 安装进 VS Code 并完成端到端验证。
5. 之后进行 UI 与性能优化。

**硬约束**（来自用户，必须遵守）：

- **不得修改桌面端的 `desktop` 档**（其中的记忆与插件为用户正在使用的内容）。
  唯一允许的例外已经执行完毕：安装了一个 ACP 接入点插件（见下文），并已掌握卸载方法。
- 不删除用户的文件。
- 不破坏现有编译环境。
- 每完成一步提交 git。
- 用户不接受比喻，要求表述平实；不明确的地方**先询问**，不得自行推断。

## 二、架构（三段式）

```
VS Code 侧边栏（扩展 UI：webview）
      │  ACP：JSON-RPC，一行一个 JSON（NDJSON）
      ▼
  ACP 接入点插件 dsh-acp-door（安装在 DSH 内核中的插件，在本机回环地址再提供一份 ACP 桥）
      │  默认监听 127.0.0.1:47821
      ▼
  正在运行的 DSH 内核（用户的桌面端，或者扩展自行拉起的无窗口内核）
```

**引入该插件的原因**：DSH 内核本体不对外提供 ACP（该协议面向编辑器），
因此通过一个内核插件在回环地址上再提供一份 ACP。该插件**只监听回环地址且没有鉴权**
（这是一个已知的安全边界，需要向用户披露：本机任何进程都能连接该端口）。

**两种运行模式**（用户明确关注过，2026-09-19 再次说明）：

- 端口上**已经有该插件**（桌面端在运行）→ 面板直接接入：一个进程、一个内核，
  不再额外启动内核。
- 端口上**没有该插件**（桌面端未启动、刚开机）→ 面板自行启动一个**无窗口**内核
  （`dsh --profile <档名> --no-open --host 127.0.0.1 --port 0`），连接该内核工作，
  关闭 VS Code 时**回收自行启动的进程**（不触碰桌面端的进程）。

因此**使用该插件不要求先打开桌面端**。这不是"后备路径"，而是**主路径之一**：
实测（2026-09-19，桌面端同时开启、测试自行选择 47830 端口）从零到可以提问用时
**5.2 秒**，握手、建会话、执行一个真实回合、回收进程全部通过；
**真实 VS Code 隔离窗口中也验证过**（13 项全部通过，11 秒建出会话；Stage A/B 之后
`DSH_PANEL_CHECK_LINGER=60` 那一轮同样为 13/13；2026-09-19 夜增加权限断言之后
为 **15 项全部通过**）—— 见下文 `vscode-check` 一段。

> **措辞约束**（用户 2026-09-19 就此提出过意见）：界面文案中**不得**出现
> "已连上正在运行的 DSH""桌面端没在跑…"这类把桌面端视为前提的表述。
> 空态文案当前为 `直接提问即可 —— DSH 会按需启动，不需要先启动桌面端。`
> （2026-09-19 立下该约束时为 `内核由插件自己按需启动，不用先去桌面上打开 DSH`）。
> 后续修改文案时应当遵守这一条。

### 界面约定（2026-09-19 确定）

- **顶栏该行只显示短状态**：`正在连接…` / `正在启动…` / `就绪` / `工作中…` / `未连接`。
  该行宽度很小，放入长句子会挤掉工作目录与耗时。`media/main.js` 的
  `shortStatus()` 另有一层保护：长文案进入 status 时只显示第一行并截断到 24 字。
- **报错进入对话流**（`{type:'error'}` → `.msg-error`），不进入顶栏。用户的表述是
  "像其他 agent 那样把报错写在对话框"。长原文保留在 `<details>原始报错（展开）</details>` 中：
  **一个字都不删除**，但不直接展示。无法识别的错误（没有对应的中文标题）属于例外 —— 原文是唯一信息，
  必须直接展示。
- **"正在启动内核"这类说明**通过 `{type:'notice'}`（对话流中居中的系统提示），
  不占用顶栏。

**已确认的一项硬限制（2026-09-17 已绕过）**：内核的 ACP 接口只提供
`initialize / authenticate / session/new / session/list / session/resume / session/close /
session/set_config_option / session/prompt` 与通知 `session/cancel`。
**没有 `session/load`** —— 即能够列出会话、能够 resume（上下文可以接回），但**无法将
历史对话正文回放给面板**。绕过方法（用户 2026-09-17 已确认）：**由该插件自行读取
`$DSH_HOME/sessions`**（多帧 zstd 解码 + 回放重建，纯函数库位于 `packages/dsh-door/lib/sessions.js`，
该插件自 0.0.8 起以 `dsh-door/sessions/list|get` 两个旁路方法对外提供，请求由该插件就地应答、不转发内核）。

## 2026-09-19 补记：`desktop` 档无法启动（用户报告的缺陷，已修复）

**症状**：用户执行 Reload Window 之后，面板报出「没能启动 DSH 内核」，档为 `desktop`，
并建议用户修改 `dshPanel.dshCommand`。

**根本原因（已查明，非推测）**：

1. `desktop` 档**由桌面端独占**，普通命令行无法启动。该档自身会明确报出：
   `error: profile "desktop" is managed exclusively by the Electron application`。
   而该档恰好是当时的默认值 —— 因此"桌面端未启动"时面板必然无法启动，
   而该场景正是最需要面板自行启动内核的场景。
2. PATH 上的 `dsh` 是**桌面端自身的垫片**：
   `set ELECTRON_RUN_AS_NODE=1 & "DSH Desktop.exe" --expose-internals .../desktop-cli.js %*`。
   该垫片**可以**运行 `desktop` 档。但它位于
   `…\host-commands\desktop\generations\<哈希>\bin\` 这类一次性目录中，
   桌面端换代即更换路径 —— 较早启动的 VS Code 进程，其 PATH 可能仍指向
   已经删除的那一代。于是 `dsh` 无法找到、`node bin.js` 又拒绝 `desktop`，
   **两条候选路径同时失败**，即用户观察到的两条失败记录。
3. 面板当时还丢弃了内核的 stderr（`stdio: 'ignore'`），因此报错内容属于**推测**
   （"多半是 dsh 不在 PATH 里"）—— 用户按该提示修改 dshCommand 只会进一步偏离原因。

**修复方法**：

- 面板增加了专用档 **`vscode-panel`**：
  `dsh --profile vscode-panel --from-default-profile web`（官方 web 模板 → 可由命令行启动、
  可开启 TCP 接入点），再通过 `dsh plugin --profile vscode-panel add <ACP 接入点插件 tgz>` 和用户那 10 个插件进行安装。
  默认配置 `dshPanel.fallbackProfile` 改为该档。
- **无法启动时更换档**：`panelProfileCandidates()` 扫描 `$DSH_HOME/profiles`，挑出
  "已安装 `dsh-acp-door` 且包含 `@deepseek-ai/dsh-web-app`"的档作为备选（设置中指定的档始终排第一）。
- **不再丢弃 stderr**：保留末尾 2000 字，`explainKernelFailure()` 可识别
  "档被独占 / 参数不正确 / 命令找不到 / 端口被占用"，可识别时按实际情况说明，无法识别时才回退到推测，
  并将原文附在后面。访问令牌、密钥、口令等敏感参数的值会替换为「[已隐藏]」，其余内容保持原样。
- 复现该问题的测试：`test/fallback.js` 第 5 节 + `test/static.js` 的候选档与退出原因相关各项。

**用户机器上留下的内容**（位于仓库之外，重建方法见 `docs/恢复方法.md`）：
`$DSH_HOME/profiles/vscode-panel/`；`$DSH_HOME/profiles/vscode/` 中额外安装了该插件
（该档用于 ACP-stdio，该插件对它无效，但安装后无副作用），修改之前保留了
`package.json.before-door.bak` / `cordis.yml.before-door.bak`。

新增代码 `src/panel/kernel-manager.js`：内核按 `host:port` 登记，并记录使用者集合。

- 面板**使用**内核 → `acquire`；面板销毁 → `release`（**仅解除引用，不终止进程**）；
- 最后一个使用者解除引用 → 进入宽限期（`dshPanel.kernelIdleMinutes`，默认 10 分钟，
  设为 0 表示旧行为"关闭即回收"）→ 到期后才回收；
- 宽限期内面板重新打开 → **继续使用同一个进程**（日志：`面板又用上这个后台 DSH 了，
  原本要收它的计时取消`）；
- **窗口关闭**（`deactivate`）与 **「DSH：停掉后台内核」**（新增命令）→ 无条件回收；
- 由其他来源启动的内核（桌面端）**始终不触碰**：未登记的内核，`release` 不会误杀任何进程。

## 2026-09-20 早：两项工作 —— 「切不了权限」的原因，与界面中内部词的清除

### 一、用户报告「为什么改了之后，我切换不了权限了？」

**处理顺序应为先读取日志，再判断原因与责任，不应先行认错或推责。** 用户机器上的面板日志
（`%APPDATA%\Code\logs\<时间戳>\window1\exthost\output_logging_*\2-DSH Panel.log`）：

```
00:50:27 端口 127.0.0.1:47821 上有现成的门，接上去（不自启内核）
00:50:28 已建会话 8837e820-…（cwd=<仓库根目录>，预设=standard）
00:50:28 权限预设读不到（old-door）："Method not found": dsh-door/permission/get
```

**实际原因**：面板接入的是**桌面端内核**（47821），而桌面端档中的连接组件为
**0.0.7**（该档由桌面端自身管理，命令行无法修改），其中不含 `dsh-door/permission/*`。
因此按钮只能显示「切不了」—— 这与当天的两轮改动（文案、顶栏宽度）**无关**，
而是"优先接入现成内核"这条路径的既有行为，用户本次恰好遇到。

**修复方式不是修改文案，而是使权限功能真正可用**：所接入的内核无法切换权限 →
**改用面板自行启动的内核**（`vscode-panel` 档，组件 0.0.12）。判据已抽为纯函数
`shouldSwitchToOwnKernel`（`src/panel/view.js`，由 `test/panel.js` §8.86 逐项验证）：

| 情形 | 是否更换 | 依据 |
| --- | --- | --- |
| `old-door`（所连接组件版本旧）+ 当前接入 `dshPanel.port` + `autoStart` 已开启 + 尚未更换过 | **更换** | 自行启动的内核使用配套的新版本组件 |
| 已经位于自行启动的内核上 | 不更换 | 更换不会产生任何变化 |
| `autoStart=false` | 不更换 | 用户明确要求不得在后台启动进程 |
| `no-service`（该 DSH 未提供权限设置） | 不更换 | 更换任何内核均无效，如实说明更有用 |
| `error`（读取失败，可能仅为网络波动） | 不更换 | 暂不改变结构 |
| 已更换过一次 | 不更换 | 不允许反复切换 |

**实现过程中的三个问题（均已实际遇到）**：

1. **判断必须由连接流程按顺序执行**。第一版将「更换」逻辑写在 `refreshPermission` 的
   catch 中（该处由 session 事件异步触发），会在外层连接流程尚未完成时再次发起
   一条连接 → 两条流程并行争用 `this.client`。现已改为在 `connectInternal` 中
   `await this.refreshPermission()` 之后**同步判断**，判断完成后立即 `return`。
2. **更换过程需要抑制中间提示**：否则用户会先读到「这个 DSH 版本旧，这里换不了权限」，
   再读到「改用面板自己启动的」，即先解释后解决，前一条说明无效。通过
   `quietPermissionNotice` + `explainPermissionOnce()` 去重。
3. **更换时只能监听自身的端口**（`ownPortOnly` / `fallbackPorts()`）：自启路径
   此前同时监听 `selfStartPort` 与 `dshPanel.port`（为兼容不识别环境变量的旧组件），
   而 `dshPanel.port` 上的旧版本接入点**持续响应** —— 因此"新内核已启动"成为假象，
   面板重新接入同一个内核，未产生实际更换效果。真实窗口自检中捕获的原文为
   `这个档里的门没认端口设置，开在了 47821`。

**未修改桌面端档**：该档由桌面端管理（`app-managed-profile`），修改风险较高。
代价：桌面端与 VS Code 面板同时开启时会存在**两个内核**（桌面端一个、面板一个）。
如需只保留一个，应将该档中的组件同步升级，并在升级后重启桌面端。

## 八、已发生的问题与规避方法

1. **`build/` 会被打包脚本清空**：`node tools/build-vsix.js` 会执行 `rmSync(build)`。
   需要保留的产物不应放在 `build/`（截图曾因此丢失一次，现已放入 `shots/`）。
2. **不得按进程名对内核执行 `taskkill`**：用户自身的 DSH Desktop 所启动的内核，其命令行中
   同样包含 `--no-open`，与扩展启动的内核外观相似。自检工具现在**不终止任何内核**，
   只回收自身开启的隔离窗口，其余仅作报告（并排除"父进程为 DSH Desktop.exe"的进程）。
3. **扩展启动的内核命令行形式**：`cmd.exe /d /s /c "dsh --profile desktop --no-open
   --host 127.0.0.1 --port 0"`；而真正的 `DSH Desktop.exe` 子进程命令行中反而**不含**
   `--profile/--no-open`。识别"是不是我们拉起的"时，应以该 `cmd.exe` 为依据。
4. **无头 Chrome 不为程序化滚动派发 scroll 事件（实测 0 次）**。界面的
   "不得将正在查看历史记录的用户拉回底部"逻辑依赖 scroll 事件判断，直接测试会得出错误结论。
   `tools/uitest.js` 中采用**手动派发**一个 scroll 事件的方式进行测试，注释中已写明原因。
5. **`tools/uitest.js` 中的断言脚本是模板字符串**：注释与代码中均不得出现反引号，
   换行必须写作 `\\n`，否则生成的脚本会直接产生语法错误。
6. **PowerShell 的引号与编码**：内联 `node -e` 中的中文、`$()`、反引号极易被吞掉。
   编写脚本或提交信息一律**使用文件**（`git commit -F 文件`）。
   **另外：修改文件不得使用 PowerShell 的 `Set-Content -Encoding UTF8`** ——
   该命令会为文件添加 UTF-8 BOM（`EF BB BF`）。2026-09-19 曾因此为该插件的
   `package.json` 添加 BOM，随后打入 tgz、安装进用户的档，结果 `dsh plugin` 每次
   都失败于 `JSON.parse`（`Unexpected token '﻿'`），等同于损坏了该档。
   修改文件应使用编辑工具；`node tools/check-eol.cjs` 会报告 BOM，
   `test/static.js` 中也有一条针对安装文件的断言。
   另有一个相关问题：`pnpm` 的 lockfile 记录 tgz 的完整性哈希，
   **删除已安装过的 tgz 或修改其内容**会导致 `pnpm add` 直接报 `ENOENT` ——
   处理方式为补回该文件，或更换版本号。
7. **`code.cmd` 会把参数转交给正在运行的实例**，因此不能用于开启隔离窗口。开启隔离窗口必须
   直接启动 `Code.exe`，并带上 `--user-data-dir` / `--extensions-dir` / `--new-window` /
   `--verbose`（缺少 `--verbose` 时输出通道日志不落盘）。
8. **切换模型必须以内核回复为准**（`setSessionConfigOption` 返回的 `configOptions`），
   不得以自身请求的值作为依据 —— 内核会对取值进行归一化。
9. **预设（agent preset）**：只有桌面端创建的会话会将 preset 写入会话记录；
   通过该插件建立的会话需要在请求中携带 `_meta['dsh-door']` 进行补挂，否则**恢复后的会话没有工具**。
10. **`dsh` 命令不在 PATH 中时**此前需要等待 120 秒才报错。现在改为监视子进程：
    子进程退出后立即说明命令错误与处理方式。该分支的测试覆盖率通过为等待函数
    增加一个仅供测试使用的超时参数实现。
11. **`$pid` 是 PowerShell 的只读变量**，循环中不得将其用作变量名。
12. **`dshCommand` 里带参数会起不来**（2026-09-17 修）。`locate.js` 原来把**整串**
    命令当作一个程序名并加引号，导致 `node D:\...\bin.js` 在 cmd 中被视为「名称中包含空格的
    程序」，退出码为 1。现在先由 `splitCommand()` 拆分，再逐段加引号。
13. **本机 `dsh` 命令不在 PATH 上**。npm / pnpm / nvm 的 bin 目录里都没有 `dsh.cmd`，
    唯一的 CLI 是 `$DSH_HOME\profiles\node_modules\@deepseek-ai\dsh\lib\bin.js`
    （v0.1.5-rc.2）。因此：
    - 扩展自启内核时，需要将 `dshPanel.dshCommand` 配置为
      `node $DSH_HOME\profiles\node_modules\@deepseek-ai\dsh\lib\bin.js`；
    - 在命令行运行需要真实内核的测试时，先设置
      `$env:DSH_PANEL_DSH = "<该 node.exe 的完整路径> <bin.js 的完整路径>"`；
    - 未设置时，`panel.js` / `smoke.js` / `fallback.js` 等套件会失败（**并非代码损坏**）。
14. **worktree 的换行符与主工作区不一致**。`<仓库根目录>` 工作区中的文件为 LF
    （上一轮使用写文件工具写入），而新建的 worktree 按 `core.autocrlf=true` 检出为
    CRLF。git 会进行归一化，因此两边的 `git status` 均显示为干净，但
    `test/helpers/door.js` 的 `doorDrift()` 采用**逐字节比对** —— 在 worktree 中会
    误报"该插件与源码不一致"，随后尝试通过 `dsh plugin` 重新安装（并再次遇到第 13 条）。
    运行该插件相关测试之前，应先将 `packages/dsh-door/**` 统一为 LF。另外，`dshdoor` 测试档
    的插件依赖指向 `<仓库根目录>/packages/dsh-door`，而非 worktree。
15. **沙箱会拦截 pnpm 的批量删除**（2026-09-17 已遇到）。`syncDoor()` 的 remove+add
    会触发 pnpm 更换依赖文件，变更数量超过阈值（实测 184 个文件、阈值 50）即被
    `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]` 拦下 —— add 失败，且**测试档
    的 `package.json` 依赖已被 remove 清空**，内核启动时不再加载该插件（症状：
    内核已启动、47821 始终未开放）。`syncDoor()` 现在对 add 失败有后备处理（按文件
    同步 lib + 手工补回依赖声明）。确需重新安装时：先将旧依赖目录**改名移开**再执行 add，
    pnpm 无需删除任何内容，可以成功。
16. **`probePort` 是单次探测，`waitForPort` 才用于等待接入点开启**。接入点需要 10~40 秒才开启，
    使用 `probePort` 判断接入点是否已开启几乎必然产生假阴性（该方法只尝试一次，连接被拒绝即
    返回 false）。等待接入点一律使用 `waitForPort(host, port, { totalMs })`。
17. **TransformStream 的 readable 若无消费方，整条数据通道即失效**（2026-09-17 已遇到，
    该插件 0.0.8 曾因此无法应答）。出站中继最初实现为 TransformStream，但没有任何一方读取
    `relay.readable` —— transform 始终不执行，内核回复始终无法发出，客户端
    观察到的是「接入点已连接但不应答」。现在出站层为 `frames.js` 的
    `createOutboundRelay()`（返回 WritableStream，由 ndJsonStream 直接写入），
    并且有「写入的行必须从 sink 输出」的测试进行约束（`test/frames.js` 第 8 节）。
18. **`dsh` CLI 不得操作 desktop 档**（2026-09-18 实测）：`dsh plugin --profile desktop
    remove/add` 会被直接拒绝（`profile "desktop" is managed exclusively by the Electron
    application`）。升级该插件只能手工修改文件（做法见第七节第 4 条）。
19. **GNU tar 将 `D:` 视为远程主机**：Windows 盘符路径（`tar -xzf D:/...`）会报
    `Cannot connect to D: resolve failed`。路径写作 `/d/...` 即可。
20. **`dsh plugin --profile desktop …` 仅在桌面端**未运行**时可用**（2026-09-18 实测）：
    桌面端运行期间，CLI 会直接拒绝（`profile "desktop" is managed exclusively by the
    Electron application`）。09-17 那次安装该插件之所以成功，原因是当时桌面端未启动。
    因此"升级桌面档中的该插件"不能按想当然处理，见第七节第 4 条。
21. **`spawn(cmd.exe, [...])` 会对参数中的引号再次转义**（2026-09-19 修复，真实缺陷）。
    Windows 上执行 `cmd.exe /d /s /c "完整命令行"` 时，如果字符串中已包含引号
    （例如程序路径含空格并已被引号括起），默认的 spawn 会再转义一次，cmd 收到
    的即成为损坏的路径。必须同时设置 `windowsVerbatimArguments: true`。
    另一个独立问题：**不得仅按空白拆分命令**。本机 dsh 的真实路径为
    `…\AppData\Roaming\DSH Desktop\host-commands\…\dsh.cmd`，路径中**含空格**，
    用户按说明"把完整路径填进设置"填写的是直接给出的路径，按空白拆分会将程序名截为两段，
    报出的错误为 `'C:\Users\…\Roaming\DSH' is not recognized as an internal or external
    command`（该文本为 cmd 原文；面板会将其转换为中文表述）。
    **注意**：cmd 的输出语言随其环境变化 —— 由脚本 spawn 时本机输出为
    英文，而面板自身的中文文案属于**翻译**（`src/dsh/errors.js` 对两种形式均可识别）。
    因此不应按"中文原文"检索日志。
    现在 `resolveCommand()` 会「优先判定整串是否为一个存在的文件」，再退到
    「将拆分错误的片段按磁盘上真实存在的路径重新拼接」（`rejoinExisting`）。
    回归测试：`test/spawn-quote.js`（16 项，**真实进程**）—— 该套件构造一个含空格的
    `.cmd` 垫片，通过真实的 `spawnBackgroundDsh()` / `runDshSync()` 执行，
    再读取垫片输出进行内容比对。必须真实执行的原因：这两个缺陷组合产生的字符串**表面上
    完全正确**，仅断言 `commandLine()` 的返回值无法捕获。该套件位于
    `run-all.js` 中，不需要 dsh、不占用端口。
22. **同一方法名被复用后，测试断言会变为验证另一项内容**（2026-09-19 修复，
    真实缺陷）。`DoorClient.listSessions()` 原为 ACP 的 `session/list`（返回
    `{sessionId, cwd}`），改为使用该插件的旁路方法（返回 `{id, title, turns}`）之后，
    `test/smoke.js` 中"验证 ACP 列表形状"那一段的**注释与断言均未同步修改** ——
    因此该插件版本偏旧时，测试以一个与被测代码无关的原因失败。现在两个方法的名称已经区分：
    `listKernelSessions()` 属于 ACP，`listHistory()`/`getHistory()` 属于该插件。
23. **两份实现必须由一条一致性测试约束**（2026-09-19）。历史会话读取现有两份实现
    （该插件为 ESM 一份、面板为 CJS 一份，原因是扩展零依赖、无法 require 该插件的 ESM）。
    仅依靠"在注释中注明需要同步"无法保证一致，因此设有 `test/sessions-parity.js`：
    同一批会话文件输入两份实现，44 项逐项比对，包括坏帧、截断、非法 id、缺少目录。
24. **失败路径上未清理的状态会污染下一次操作**（2026-09-19 修复，真实缺陷）。
    `decorateLine()` 的预筛条件为 `line.includes('"result"')`，因此**仅含 error、
    不含 result** 的回复完全没有被处理：`state.queue` 中对应的预设点名始终不被清理。该点名按
    "发出顺序"领取（`session/new` 时 sessionId 尚不可知），因此**下一次**建会话
    会领取到上一次失败时记录的预设 —— 用户未指定预设却被应用了其他模式。
    修复方法：出错回复同样需要处理（将该点名从队列中移除）。回归测试位于
    `test/frames.js` 第 8 节第 (6) 段。
25. **"等待一个 promise"必须设定上限，否则故障表现为"消息静默消失"**（2026-09-19 修复）。
    入站闸 `holdUntilMounted()` 原为 `await waiting.catch(() => {})`，
    未设置超时。挂载链内部均已 catch，唯一未覆盖的情形是内核某个服务返回**永不落定**
    的 promise —— 此时 `session/prompt` 被永久阻塞：用户已发送消息，界面上没有任何
    反应，也没有任何报错可查。现在入站与出站使用同一上限（`MOUNT_WAIT_MS`，
    通过 `frames.js` 的 `waitForMount()`），到期即放行，最坏退化为"该会话没有可用工具"。
26. **PowerShell 5.1 的 `Get-Content -Raw` 会将 UTF-8 读为乱码**，`ConvertFrom-Json`
    随之解析失败（2026-09-19 连续遇到两次）。读取 JSON 一律使用 Node（`JSON.parse(fs.readFileSync)`），
    不使用 PowerShell 的 JSON 命令。同理：内联 `node -e "…"` 中的引号与反引号极易被
    PowerShell 吞掉 —— **应写入 `.cjs` 文件后执行**（临时脚本放在 `build/`，该目录不入库）。

## 九、自检工具的适用范围

- `test/*` 大多使用模拟客户端与模拟 vscode，执行速度较快，但不覆盖"用户能否找到入口"这类真实环境问题。
- `tools/vscode-check.js` 通过 `DSH_PANEL_AUTOFOCUS=1` 使扩展**自行**打开面板，
  因此它验证了"激活 → 展开 → 握手 → 建会话"整条链路，但**恰好绕过了"用户是否能够操作到"**。
  这正是早上出现问题的环节：**自动化通过不等于人可以正常使用**。人机交互环节应当由用户实际试用一次。
- 断言自身也需要被验证：曾有一条"消息间距一致"的检查写作"消息数 ≥3 时才检查"，
  而场景中只有 2 条消息 —— 该检查从未执行（无效代码）。

## 十、与用户的协作约定

- 用户原话："有什么不明确的问题一定要来问我（用通俗易懂的话），不要自己想怎么搞怎么搞"。
- 用户原话："不要用你那奇妙的比喻，说人话"。
- 用户对界面美观要求较高；**UI 阶段必须等待用户提供的样稿**（用户原话："这个能最后再做吗？
  如果可以的话就先放一下吧，记得要做的时候提醒我给你样稿"）。
- 不得删除用户的内容（包括测试产生的会话记录）。
- 每完成一步提交 git。
