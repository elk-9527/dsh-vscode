## 二、修复的缺陷（4 个，均有回归测试）

### 1. dsh 路径含空格时无法启动（上一轮仅修复一半）

**症状**：面板无法接入、也不会自行启动后台内核，报错为
`'C:\Users\…\Roaming\DSH' is not recognized as an internal or external command`
（cmd 的原始输出；面板会将其转换为中文文案"不是内部或外部命令"后显示）。

**根因**（两个独立缺陷叠加）：

- `dsh` 的实际路径为 `…\AppData\Roaming\DSH Desktop\host-commands\…\dsh.cmd`，
  **路径中包含空格**。原有代码按空白字符拆分命令，程序名因此被拆成两段。
  设置项说明与面板报错文案均提示用户"把完整路径填进设置"——按此操作即触发该问题。
- 即使用户自行添加引号也无效：`spawn(cmd.exe, [...])` 会对参数中的引号**再次转义**，
  cmd 收到的是损坏的路径。必须同时设置 `windowsVerbatimArguments: true`。

**修法**：`resolveCommand()` 先判断整串是否为一个存在的文件（是则整段作为程序名），
否则按空白拆分，再按磁盘上确实存在的片段将拆分结果重新拼接。
配套新增一个**真实进程**回归套件 `test/spawn-quote.js`（16 项：构造一个含空格的 `.cmd`
垫片，使用真实的启动逻辑运行，再读取该垫片收到的参数）。

**该问题优先级最高的原因**：本机 `dsh` 路径包含空格，**必然触发**该问题。

### 2. 一次失败的建会话，会把预设串到下一段对话

**症状**：未指定预设、或指定了另一个模式时，新会话仍挂载上一次的模式。
仅在"出现过一次建会话失败"之后出现，属于难以定位的类型。

**根因**：该插件记录"客户端指定了哪个预设"依赖一个队列（`session/new` 阶段会话 id
尚未确定，只能按发送顺序排队，等待 `agent/created` 领取）。但请求**失败**时不会有
`agent/created` 前来领取，该条目持续留在队首 —— 被**下一次**建会话取走。
错误回复完全未被处理，因为预筛条件要求"该行中必须包含 `result`"。

**修法**：错误回复同样需要处理 —— 将对应的预设指定从队列中移除。该行为已由回归测试覆盖。

### 3. 消息有可能永远发不出去（且毫无提示）

**症状**：极端情况下发送消息后，界面无任何反应，也没有任何可查的报错。

**根因**：入站方向存在一处阻塞点，在会话的预设挂载完成之前会阻塞 `session/prompt`
（该行为正确，否则模型没有可用工具）。但该等待**没有超时**：
`await waiting.catch(() => {})`。挂载链内部均已 catch，唯一未被覆盖的情况是内核
某个服务返回一个**永不落定**的 promise —— 此时该消息被永久阻塞。

**修法**：入站与出站使用同一上限（15 秒），超时即放行。最坏情况退化为"该会话没有
可用工具"（可观察、可重试），而不是"消息无任何响应"。

### 4. 读历史失败时的提示指向无效操作

**症状**：点击历史按钮，得到提示"接入点插件太旧（需要 dsh-acp-door 0.0.8 以上）。
重启桌面端 DSH（或重装接入点插件）后再试。" 按提示操作之后，仍显示同一提示。

**根因**：该插件安装在**用户档**中，而该档由 DSH 桌面端管理。
桌面档中安装的该插件为 **0.0.7**，且**无法升级**（桌面端运行期间 CLI 直接拒绝，
见第三节）。因此该提示将"扩展自身的依赖问题"转嫁给用户，且给出的解决路径不可行。

**修法**（本轮收益最高的一处）：**面板不再依赖该插件的版本**。
接入本机时，历史会话由**面板自行读取** `$DSH_HOME/sessions` —— 面板与内核位于
同一台机器上，会话文件即在磁盘上，不存在无法读取的理由。该插件的两个旁路方法仍然
优先使用（接入**其他机器**上的该插件时只能依赖它们），该插件版本过低时自动回退到
自行读取，**不再向用户提示**。

实测：**86 段会话、0 段解码失败、1.34 秒**读取完成。

### 另有两套持续失败的测试

接管时 `node test/run-all.js --all` 为**失败状态**，两个套件失败：

- 「面板层」8.9：历史清单是空的。
- 「端到端」第 7 节：报 `session/list 能调通 —— "Method not found": dsh-door/sessions/list`。

**测试中的注释与断言未同步修改** —— 因此断言实际校验的是另一项行为，该插件版本较旧时
即以与被测代码无关的原因失败。现在两个方法名已分开
（`listKernelSessions()` / `listHistory()`），测试各自校验对应行为。**这两条当前均通过。**

## 四、界面收尾（3 处）

用户曾表示"按你的审美改一下"。需先说明：**配色未作改动** —— 2026-09-17 用户确认的方案是
"完全交给 VS Code 主题，不加自己的强调色"，该方案已遵循。本次修改的是三处
**属于功能缺失而非偏好差异**的问题：

1. **历史浮层无法通过 Esc 关闭，焦点未随之转移。** 该浮层覆盖整个面板，但打开之后
   焦点仍停留在下层**不可见**的控件上 —— 键盘操作时 Tab 焦点落在不可见元素上；
   关闭只能通过连续 Tab 定位到右上角的 ×。当前行为：Esc 可关闭、打开时焦点移入浮层、
   关闭后焦点返回触发按钮，并声明了 `role="dialog" + aria-modal`。
2. **读历史失败原有实现复用了"空状态"样式**（居中的灰色文字）—— 会被理解为
   "你没有历史会话"。而这两种情况的处理方式完全不同（一种无需处理，一种需要修复）。
   当前错误状态有独立样式：左对齐、警示色边框、`role="alert"`。
3. **回放原有实现停在最后一句，"这是回放"提示也位于结尾。** 现改为停在**开头**、
   将该提示置于**开头**。理由：该提示需要防范的是一种实际会发生的情况 —— 用户对着
   历史内容直接输入，误认为在与该段上下文对话。该提示出现越早越好，且回放的使用
   方式本身即为从头阅读。

另外 `uitest.js` 新增 15 项断言覆盖这三处（当前共 387 项）。
