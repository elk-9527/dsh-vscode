# DSH 双插件兼容维护流程

## 维护目标与边界

维护对象为 VS Code 扩展 `dsh-acp-panel` 与 ACP 接入点插件（`dsh-acp-door`）。每次 DSH 更新按本文执行；先记录环境与失败，再修改兼容层。版本范围变更本身不构成兼容证明。首轮目标为 DSH `0.2.0-rc.2`，原有 `0.1.5-rc.2`、`0.2.0-rc.1` 继续列入回归范围。

仅维护本机 Windows 接入、自启、会话、模型、权限、历史与配置继承。第三方插件能力联动不在本轮范围内。市场发布由维护者显式执行。

## 更新后的固定步骤

| 步骤 | 操作 | 输出与完成条件 |
| --- | --- | --- |
| 记录基线 | `pnpm compat:doctor -- --json`；记录源码、运行时及已安装插件 | 脱敏诊断；区分源码版本与装机版本 |
| 比较更新 | 阅读官方 release；核对启动入口、peer dependency、服务与事件接口 | 变更清单；不可只查看版本号 |
| 复现问题 | `pnpm compat:test -- --dsh <精确版本>` | 每个失败阶段的日志与报告；保留首次失败报告 |
| 完成适配 | 修改内核、启动或配置适配层；为实际失败增加回归用例 | 快速套件与契约套件通过；避免扩散版本判断 |
| 联合验收 | 隔离真实内核、测试模型服务、真实模型与最终安装包 | 必测项目全部通过；跳过、下载失败和环境缺失不等于通过 |
| 安装与发布 | 备份后安装候选包并完成本机验收，再执行 `pnpm compat:release-check` | 装机文件一致；记录测试证据、包校验值与回退方法 |

官方版本来源为 `deepseek-ai/deepseek-harness` 的 GitHub Releases 及 npm 官方注册表。预发布版纳入检查；分别记录 npm 与 Desktop 发行方式，不能以 npm 内核通过代替 Desktop 启动通过。

## 工具与证据

- `compat:doctor` 只读检查 DSH 安装、Desktop 内置版本、CLI 候选、两个配置集的安装状态、peer 声明与 ACP 状态；默认文本，`--json` 输出结构化脱敏结果。不得写配置、安装插件或启动内核。
- `compat:test -- --dsh <版本>` 使用隔离的 `DSH_HOME`、临时工作目录和空闲回环端口。默认使用本机匹配版本；`--install` 在隔离目录取得指定 npm 发行版。`--command <命令>` 可指定启动入口。真实测试安装打包后的接入点插件，不直接复制源码作为安装成功证明。
- `compat:test -- --discover` 查询官方稳定版及预发布版，输出精确版本的 CI 矩阵。获取失败记录为 `acquisition-failed`，接口或功能失败记录为 `failed`，环境缺失记录为 `unavailable`。
- `compat:test -- --dsh <版本> --record` 在全部必测通过后显式登记矩阵，公开的版本、摘要与检查状态写入 `compat/evidence/public-*.json`；也可用 `--record-report <已完成报告>` 登记同一源码指纹的报告。完整运行资料保留在本地，新候选先建立 `pending` 条目，CI 不自动登记支持。
- `compat:local` 验收已安装候选包：`--mode attach` 记录桌面接入；桌面完全退出后 `--mode self --desktop-closed` 对比配置并执行真实模型文件工具；`--mode editor --path attach|self` 从最终 VSIX 解包并在隔离编辑器验证对应路径；`--mode installed` 比对装机文件。各次运行使用同一个 `--out build/compat/local-report.json` 汇总证据。
- 编辑器测试同时隔离 `--user-data-dir`、`--extensions-dir` 与 `--shared-data-dir`，并禁用测试不需要的 GitHub、微软登录提供方。清除子进程中的便携模式覆盖，拒绝与日常目录重叠的路径及路径别名；回收窗口按本次确切用户数据目录判断，不能仅按“启动后新增 PID”判断。Windows 的 GitHub 共享账号存储不受单独的 `--user-data-dir` 隔离保护。
- `compat:release-check -- --report <内核报告> --local-report <本机报告>` 核对源码版本、兼容声明、更新说明、矩阵、必测结果和安装包校验值。未提供合格报告时阻止发布验收。脚本不向市场发布。
- 机器专属报告与日志写入 `build/compat/`，不提交原始会话、模型凭据与访问令牌。报告包含时间、Git 提交及工作区状态、DSH/Node/ACP/两个插件版本、发行方式、阶段结果和包 SHA-256。
- `compat/versions.json` 是兼容矩阵，状态为 `pending`、`passed` 或 `failed`。只有证据齐全且版本与安装包一致时才能登记通过；历史 README 不构成证据。真实模型和 Desktop 验收单独登记。

## 必测项目与接口规则

自动化内核验收覆盖：加载打包插件、ACP 握手、状态能力、新建会话、模型与模式清单、流式输出及去重、工具执行与权限问答、权限切换、历史读取、取消、断线接回和进程回收。CI 使用本机测试模型服务，避免生产凭据与外部模型波动。

本机发布验收追加：Desktop 已运行时接入同一内核；Desktop 完全退出后面板自行启动；默认模型与完整模型目录、注册表插件和官方 bundle、desktop patch 继承；真实模型至少一轮对话和工具调用；解包后的 VSIX 在隔离 VS Code 中激活、连接及回收；装机文件与安装包一致。

DSH 版本差异集中在接入点的内核适配与面板的启动/配置适配。现有 ACP 与 `dsh-door/*` 方法保留兼容；状态新增字段为可选字段。能力依据实际服务接口报告，未知接口不得宣称可用。必要能力缺失明确失败，可选能力缺失允许降级并记录原因。

## CI 与恢复

提交 CI 运行快速、兼容契约、界面及安装包检查。每日和手动任务取得官方精确版本，对支持版本和新候选版本运行真实内核验收并上传报告。任一必测跳过或失败使任务失败；获取失败单独显示，不能自动扩大支持范围。每日重新运行验收，避免旧 npm 发行物的依赖范围变化被历史缓存掩盖；不自动通知或发布。

安装前保留原 VSIX/tgz，备份目标配置集的 package、锁文件和 patch，并记录现有依赖路径。安装后重启对应内核、Reload Window，再检查实际版本与文件摘要。测试只管理自身进程；日常 Desktop 重启前应确认没有正在执行的任务。

回退插件仅恢复操作前状态，不能证明旧插件与新 DSH 可用。恢复可用组合需要使用已验收的 DSH 与两个插件版本；涉及会话格式迁移时不得直接降级日常数据，应先在备份副本上验证。原配置引用的 `file:` 安装包在切换成功前不得移动或删除。

## 候选包本机安装与回退

`node tools/compat/install-local.cjs --yes` 安装 `build/` 下的候选 tgz 与 VSIX。执行前退出空闲 Desktop；安装器保存配置、锁文件、原插件目录与旧扩展目录到 `backup/compat-<时间>/`，完成逐文件核对，并记录操作。失败时保留备份与错误；不能把包版本号已变当作安装完成。

接入点在 Desktop 的 bundle 清单和 patch 两层均应启用；安装器只补齐该 bundle，并将明确的 `acp-door / disabled: true` 恢复为 `false`，其他 patch 内容保留。持久安装来源采用 `build/install/<版本>-<SHA前缀>.tgz`，避免同号重建命中旧缓存；该文件被 profile 的 `file:` 依赖引用，不得随普通构建缓存清理。

供应链策略拒绝安装时先记录包名、精确版本和拒绝原因，不自动降低策略。经显式授权，可使用 `--offline-exemption billion-context@0.1.175` 仅为该次离线操作增补固定版本；原豁免列表按精确允许集合传入命令行。pnpm 同包名只采用首条规则，因此原有重复项在命令行合并为精确版本并集；workspace 和全局配置不修改。其他版本需要重新评估，不可复用此参数。

恢复时先退出相关内核，保留失败后的状态副本，再将原 `package.json`、锁文件与 patch 从首次操作备份复制回各配置集，使用对应 DSH 的 `plugin --profile <配置集> install --frozen-lockfile --offline` 恢复依赖。原 tgz 保持在备份记录的位置；依赖重装失败应如实记录。旧扩展可由备份目录重新构建 VSIX并用 `code --install-extension <旧包> --force` 安装；随后重新加载窗口并验证文件和版本。旧插件被新 DSH 排除时，此步骤只恢复原状态，不构成可用性恢复。
