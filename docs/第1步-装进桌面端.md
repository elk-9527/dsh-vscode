
第一行是「有这个包」，第二行是「启动时加载它」。

```powershell

```

**没有改** `cordis.patch.yml`（门自带 bundle 补丁，加进 bundles 就够了），
**没有碰**任何记忆、会话、凭据文件。

```powershell

```

然后确认 `package.json` 里 `dsh.profile.bundles` 中的 `"dsh-acp-door"` 也去掉了
（`remove` 一般会一并清掉；没有就手删）。或者直接拿上面的备份覆盖回去：

```powershell
Copy-Item D:\dsh-vscode\backup\desktop-profile-20260917-003620\* `
          C:\Users\Lenovo\.dsh\profiles\desktop\ -Force
```

## 一个必须知道的后果

**你此刻正在运行的那个 DSH Desktop 进程，还没有加载门。**

插件是在进程启动时加载的，装包不会插进已经在跑的进程里。
所以现在有两种情况：

- **你先启动 DSH 桌面端，再开 VS Code 面板** → 面板直接连上桌面端那一个进程。
  一个进程、一个大脑，这是最理想的状态。
- **你直接开 VS Code 面板（桌面端没跑或没开门）** → 扩展自己拉一个后台内核，
  用的还是 desktop 这个档，记忆、技能、插件完全一样，只是多了一个进程。

换句话说：**重启一次 DSH 桌面端（或者重启电脑），就进入第一种状态。**
在这之前，第二种也能用，只是会同时存在两个内核。

## 附：门源码差点丢了一次

升级途中我为了图方便，把测试档的依赖换成了 `link:`（真符号链接），
结果 pnpm 在清理时**把源码目录一起清空了**（`packages/dsh-door` 变成空目录）。
发现时 git 状态是 4 个文件 `D`。当时能救回来，是因为档里装的那份拷贝是完整的 ——
用它拷回源码、立刻另存了一份备份、并用 71 项纯函数测试确认没丢东西。

两条教训（已写进 `packages/dsh-door/README.md`）：

1. **别用 `link:`**，`file:` 才是对的（虽然它是拷贝）。
2. `file:` 是拷贝且有缓存，**改了源码必须重新 `add` 一次** ——
   现在 `test/helpers/door.js` 每次跑测试前会逐字节比对，不一致就自动重装，
   免得测试悄悄测了旧代码。
